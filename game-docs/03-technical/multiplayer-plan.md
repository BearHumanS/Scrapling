## 1. 전략 요약

멀티플레이는 **후속 단계**다. 단, **1단계 싱글부터 멀티 확장이 가능하도록**
설계 원칙을 미리 지킨다. 핵심: **결정적 로직 + 명령 기반 + 권위 모델**.

```
1단계: 싱글(AI 봇)  →  2단계: 온라인 멀티(친구/공개)
        ↑ 동일 룰·동일 인터페이스로 설계해 전환 비용 최소화
```

## 2. 단계적 설계 원칙 (싱글에서 미리 지키기)

1. **명령(Command) 기반 입력**: 모든 행동(주사위/구매/건설/전투행동)을
   직렬화 가능한 명령으로 표현 → 네트워크 전송·재현 용이.
2. **결정적 시뮬레이션**: 동일 명령열 + 동일 시드 → 동일 결과(부동소수 주의,
   정수/고정소수 위주).
3. **권위(Authority) 분리**: 게임 상태 변경은 권위 측이 확정, 클라이언트는 표현.
4. **AI = 가상 플레이어**: AI도 명령을 내는 동일 인터페이스 → 멀티에서 자리만 교체.

## 3. 네트워크 모델 (보드게임 특성)

- 보드게임은 **턴제**라 실시간 FPS류보다 동기화가 단순.
- **권장: 호스트(서버) 권위 + 턴 기반 명령 전달.**
  - 각 플레이어는 자기 턴에 명령 전송 → 호스트가 검증·적용 → 결과 브로드캐스트.
  - 난수는 호스트에서 생성·전파(시드 동기화)로 치팅·불일치 방지.
- **Godot High-Level Multiplayer**(RPC/MultiplayerSynchronizer) 활용.

## 4. 접속/세션

| 옵션 | 설명 | 비고 |
|------|------|------|
| **Steam P2P/로비** | GodotSteam 로비·릴레이 | 친구 초대 자연스러움(권장 1순위) |
| 전용 서버 | 별도 서버 호스팅 | 운영비·복잡도↑(필요 시 후순위) |
| 직접 IP/LAN | 단순 연결 | 테스트·로컬용 |

> 1차 멀티는 **Steam 로비 + 호스트 권위** 조합이 인디에 현실적.

## 5. 동기화 대상 / 비대상

- **동기화**: 보드 상태, 영지 소유, 플레이어 자산/스탯, 턴 순서, 전투 결과, 난수 시드.
- **로컬 처리**: 연출/애니메이션/사운드(결과만 동기화, 표현은 각자).

## 6. 마이그레이션 경로

1. 싱글 코어를 **명령+결정적**으로 구현(1단계 동안 준수).
2. 입력 레이어를 "로컬 명령" → "네트워크 명령"으로 추상화.
3. 호스트 권위/검증 계층 추가, RPC로 명령·결과 전파.
4. Steam 로비/매치 연동, 재접속·드롭 처리.
5. 베타 테스트(지연·드롭·치팅 시나리오) → 정식 멀티.

## 7. 리스크

- 결정성 깨짐(부동소수/이터레이션 순서/난수) → 데스싱크. **초기부터 규율 필요.**
- 재접속/연결 끊김 처리 복잡도.
- AI↔플레이어 인터페이스가 다르면 전환 비용 급증(처음부터 통일).
- 상세: [risk-register](../05-production/risk-register.md).
