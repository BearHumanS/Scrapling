# 03. 기술 설계 (Unity 6 기준)

## 1. 전체 아키텍처

싱글 중심 게임이므로 **클라이언트 로직 + 얇은 백엔드(BaaS)** 구조. 자체 서버는 만들지 않는다.

```
[Unity 클라이언트]
 ├─ Core (엔진 비의존 순수 C# — 게임 규칙/전투/보드 로직, 단위 테스트 대상)
 ├─ Presentation (씬, 프리팹, 연출, UI — Core의 이벤트를 구독)
 ├─ Data (ScriptableObject 정의 + JSON 밸런스 테이블)
 └─ Services (저장, 광고, IAP, 분석 — 인터페이스로 추상화)
        │
        ▼
[Firebase] Analytics / Crashlytics / Remote Config / (후순위) Cloud Save·랭킹
```

**핵심 원칙: 게임 규칙(Core)과 연출(Presentation)의 분리.**
주사위 결과, 이동, 전투는 Core에서 즉시 판정 완료 → Presentation이 결과를 받아 연출만 재생. 이렇게 하면 ① 단위 테스트 가능 ② 오토/배속 구현이 공짜 ③ 나중에 리플레이·비동기 랭킹 검증에 재사용 가능.

## 2. 주요 모듈 설계

### 2.1 보드/런 상태 머신

```
RunState:  Town → RunSetup → FloorPlaying → BossFight → FloorClear(하강/귀환 선택) → RunResult → Town
FloorTurn: WaitInput → RollDice → Moving → ResolveTile → (Battle | Event | Shop | ...) → TurnEnd
```

- `FloorGenerator`: 층 번호 + 시드 → 타일 배열 생성 (규칙 기반 랜덤, 02 문서의 비율 준수)
- **시드 기반 결정론**: `System.Random(seed)` 하나로 층 생성·드롭·이벤트를 모두 파생 → 일일 던전(고정 시드)과 버그 재현이 공짜로 해결됨. `UnityEngine.Random` 사용 금지(전역 오염)

### 2.2 전투

- `BattleSimulator` (순수 C#): 유닛 리스트 + 행동 입력 → 결과 이벤트 스트림 출력
- 스킬/버프는 **데이터 주도**: 효과를 `EffectOp`(Damage, Heal, AddStatus, ModifyDice…) 리스트로 기술 → 신규 스킬을 코드 수정 없이 테이블로 추가

### 2.3 데이터 파이프라인

```
구글 시트 (기획자 편집)
   → 시트 export 스크립트 (Apps Script or Python) → JSON
   → StreamingAssets/tables/*.json (버전 필드 포함)
   → 런타임 로더가 파싱 → 읽기전용 테이블 객체
```

- 테이블 종류: 몬스터, 스킬, 장비, 유물, 타일 규칙, 층 스케일링, 상점 풀, 이벤트, 로컬라이징
- ScriptableObject는 프리팹·아이콘 참조 등 **에셋 연결용**, 수치는 JSON — 밸런스 패치를 Remote Config로 핫픽스 가능

### 2.4 저장 시스템

- 로컬: JSON 직렬화 + AES 암호화 + 체크섬, 이중 슬롯(쓰기 실패 대비 백업)
- 저장 시점: 타일 이벤트 처리 완료마다 (강제 종료 = 이어하기, 리롤 어뷰징 방지)
- 저장 데이터 분리: `PlayerProfile`(영구: 소울스톤, 유물, 해금) / `RunSave`(진행 중 런 스냅샷)
- 스키마에 `version` 필드 + 마이그레이션 함수 체인 (업데이트 대비)
- 클라우드 세이브(기기 이전)는 소프트론칭 후 Firebase로 추가

### 2.5 연출/성능

- 주사위: 3D 리지드바디 굴림 연출이되 **결과는 선판정** — 물리 결과와 무관하게 마지막에 스냅 (연출은 손맛용)
- 이동/피격/UI 트윈: DOTween 시퀀스
- 오브젝트 풀링: 데미지 텍스트, 이펙트, 몬스터
- 타깃: 중저가 기기(갤럭시 A25급) 60fps, 발열 관리 위해 대기 화면 30fps 스로틀
- 메모리: 층 전환 시 Addressables로 테마 에셋 로드/언로드

## 3. 프로젝트 구조

```
Assets/
 ├─ _Project/
 │   ├─ Scripts/
 │   │   ├─ Core/          (asmdef: 엔진 비의존, NUnit 테스트)
 │   │   │   ├─ Board/     FloorGenerator, TileResolver, DiceRoller
 │   │   │   ├─ Battle/    BattleSimulator, EffectOp, StatusSystem
 │   │   │   ├─ Meta/      PlayerProfile, RelicSystem, EconomyRules
 │   │   │   └─ Data/      테이블 모델, 세이브 모델
 │   │   ├─ Presentation/  BoardView, BattleView, UI/
 │   │   └─ Services/      SaveService, AdsService, IAPService, AnalyticsService (인터페이스+구현)
 │   ├─ Prefabs/  Art/  Audio/  Tables/(JSON)
 │   └─ Scenes/   Boot, Town, Run
 └─ Tests/        CoreTests (전투 공식, 층 생성 비율, 세이브 마이그레이션)
```

## 4. 멀티플레이(후순위) 방침

- 1차 출시: 완전 싱글 + **비동기 경쟁**만 (일일 던전 고정 시드 점수 랭킹 — 서버는 점수 제출 API만 필요, Firebase로 충분)
- 치팅 대응: 시드+입력 로그를 함께 제출 → 서버(Cloud Functions)에서 Core 로직으로 리플레이 검증 (Core를 순수 C#으로 만든 이유)
- 실시간 대전(모두의마블식)은 별도 프로젝트 수준의 공수 — 지표가 검증되기 전에는 착수하지 않음

## 5. QA / 개발 편의

- 치트 콘솔(개발 빌드): 층 점프, 골드/장비 지급, 시드 고정, 전투 즉시 승리
- 시뮬레이션 테스트: Core만으로 1,000런 자동 플레이 → 층별 사망률·재화 수급 통계 출력 (밸런스 검증 자동화)
- CI: GitHub Actions에서 Core 단위 테스트 + (가능 시) Unity 빌드 검증
